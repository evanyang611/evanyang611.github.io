## 1 背景

**メモリは「汎用的な質問応答」から「個人のアシスタント」へ進むための鍵です。** 従来の検索・質問応答システムは、主にキーワード照合と短い文脈に依存するステートレスな仕組みで、やり取りは毎回独立しています。一方、AI エージェントでは**継続性と推論能力**が重要です。現在の課題は次のとおりです。

1. **コンテキストウィンドウの制約：** LLM の文脈長は拡大していますが、ユーザーの数年分の履歴をすべてプロンプトへ入れると、コストと遅延が増えます。
2. **パーソナライズの不足：** 汎用モデルは、ユーザーの好み、専門分野、行動習慣を知りません。
3. **対話の断絶：** 昨日「近くでデートに向くレストラン」を尋ね、今日「どこへ行くんだっけ？」と聞いても、記憶がなければ答えられません。

エージェント時代の機会は、対話データだけでなく、**行動・取引データ（Action / Transaction）**も統合できることです。メモリモジュールは、異なる形式のデータをエージェントが理解できる知識へ変換します。

## 2 定義と目標

### 2.1 定義

AI エージェントのメモリは、**動的な読み書きシステム**です。人間の脳の働きに着想を得て、大量の生データを圧縮し、構造化して保存し、必要なときに正確に取り出します。単なるデータベースではなく、**保存・検索・内省の循環**です。

### 2.2 主な目標

1. **パーソナライズ：** 味の好み、状況、予算など、過去の傾向に基づく的確な提案。
2. **継続性：** 複数ターンの対話を支え、文脈中の対象を覚えておくこと。
3. **成長：** やり取りを重ねるほど理解が深まり、「人気のもの」から「あなたが好きなもの」へ提案が変わること。

### 2.3 利用場面

| 場面 | 内容 | 例 |
| --- | --- | --- |
| **明示的な要望** | ユーザーが個別対応を直接求める。メモリを検索し、判断して提案する。 | よく行く四川料理店に似た店を提案する／味の好みをまとめる／好みに基づいて提案する。 |
| **暗黙の要望** | 明示されなくても、記憶を使うと結果が良くなる。プロフィールから好み、予算、普段の地域などを補う。 | 適切な例：「望京の近くのおいしい店」。不適切な例：「長沙の地元の人が最も勧める火鍋」。 |
| **状況への対応** | ユーザーの短期的な状態を把握する。 | 「最近風邪をひいた」→ あっさりした料理を優先 → 後で回復を尋ねる。 |
| **セッションメモリ** | 短期の文脈を引き継ぐ。 | 直前に見た店や投稿を踏まえて、次に関連情報を提案する。 |

公開ベンチマークや関連論文では、次の観点と指標がよく使われます。

| 評価観点 | 指標 | 使用頻度 | 評価方法 | 代表的なベンチマーク・論文 | 判断する価値 |
| --- | --- | --- | --- | --- | --- |
| **記憶の想起** | Accuracy / EM | ⭐⭐⭐⭐⭐ | 過去について質問し、正しい記憶に到達できるか調べる。 | MemoryBank / MemoryAgentBench / MemBench | あらゆる体系に共通する最低条件。 |
| | Recall@K | ⭐⭐⭐⭐⭐ | 検索が重要な根拠を拾えているか調べる。 | LoCoMo / MemBench | Accuracy よりメモリ構造の良し悪しがわかりやすい。 |
| **実際の記憶への依拠** | Response Correctness | ⭐⭐⭐⭐ | 回答が実際の履歴に基づき、捏造されていないか確認する。 | MemoryBank | もっともらしい作り話を防ぐ。 |
| **長期的一貫性** | Contextual Coherence | ⭐⭐⭐⭐ | 複数ターンで口調、人物像、状態が一貫しているか確認する。 | MemoryBank / LoCoMo | 主観的だが、プロダクトとして重要。 |
| **時間・因果の理解** | Temporal / Multi-hop QA | ⭐⭐⭐⭐⭐ | 時間や複数イベントをまたぐ推論を評価する。 | LoCoMo / EventQA | 長期記憶と長い文脈の違いを示す。 |
| **イベントのモデル化** | Event Summarization (FactScore) | ⭐⭐⭐⭐ | 出来事の時系列を正しく復元できるか評価する。 | LoCoMo | 文体ではなく事実を評価する。 |
| **記憶の更新** | Selective Forgetting Accuracy | ⭐⭐⭐⭐ | 新しい事実が古い事実を置き換えるか確認する。 | MemoryAgentBench / MemBench | 業界全体で失敗しやすい点。 |
| **オンライン学習** | Test-Time Learning Accuracy | ⭐⭐⭐⭐ | 履歴の例から新しい規則を学べるか評価する。 | MemoryAgentBench / Evo-Memory | エージェント時代の重要能力。 |
| **内省・抽象化** | Reflective Memory Accuracy | ⭐⭐⭐⭐ | 複数の事実から好みやプロフィールをまとめられるか調べる。 | MemBench | 人物像やユーザー洞察につながる。 |
| **規模への頑健性** | Memory Capacity Curve | ⭐⭐⭐ | ノイズが増えると性能が急落するか調べる。 | MemBench | 実装・本番運用で重要。 |
| **システム効率** | Read / Write Latency | ⭐⭐⭐ | 保存と取り出しの時間コストを測る。 | MemBench | 実運用できるかを左右する。 |

## 3 業界調査

モデルやプロダクトを横断する共通認識は、**メモリが長期的なパーソナライズとタスクの継続性を支える基盤**だということです。基本的には 3 つの操作で構成されます。

1. **書き込み：** 対話、行動、タスクから、再利用できる好み、制約、出来事、知識を抽出する。
2. **処理・管理：** 統合、抽象化、重複除去、忘却、矛盾解消、構造化を行う。
3. **読み込み：** 必要なときに検索してモデルに与え、クエリの書き換え、推論、判断、結果の絞り込みを支援する。

目標は「文脈を長くすること」から次の方向へ発展しています。

- ユーザープロフィールを作る：**誰なのか**。
- 行動の時系列を残す：**いつ、何をしたか**。
- タスク単位の推論を支える：**今と次に何をするか**。

### 3.1 学術分野の発展

研究は大きく 3 段階に分けられます。

| 段階 | 名称 | メモリの形 | 技術的な特徴 | 解決する問題 | 主な限界 | 代表例 |
| --- | --- | --- | --- | --- | --- | --- |
| **Stage 1** | 短期・試行内メモリ | 対話履歴、軌跡、要約 | 履歴の連結、要約による圧縮 | 多段階の推論、タスク内の一貫性 | タスク終了時に消える | 初期の Generative Agents / MemGPT |
| **Stage 2** | 外付けの長期メモリ：Memory as Component | ベクトル・KV・グラフなどの外部保存 | 抽出 → 保存 → 検索、セッション間で利用 | 対話をまたぐ記憶、好みの再利用 | 断片化、一貫性の弱さ、人物像が組み込まれていない | Mem0 / A-Mem / Zep / MemoryBank |
| **Stage 3** | システム全体のメモリ：Memory as Operating System | 階層化した長期記憶 | STM / MTM / LTM、イベントストリーム、自動更新と忘却 | 長期的な人物像の一貫性、タスクをまたぐ成長 | 実装が複雑で、まだ探索段階 | MemoryOS / EverMemOS / MIRIX |

主要アプリの段階を判断する観点：

| 観点 | Stage 2：コンポーネント | Stage 3：システム |
| --- | --- | --- |
| **自動で書き込むか** | 「覚えて」といった明示的なきっかけが必要。 | モデルやシステムが自動抽出する。 |
| **更新・上書きできるか** | 基本的には弱い。 | 矛盾の解消や訂正に対応する。 |
| **時系列があるか** | ない、または弱い。 | 明確なイベントストリームがある。 |
| **行動方針に影響するか** | 主に回答へ影響する。 | 計画やツール選択にも影響する。 |

この調査では主要システムを次のように位置づけています。

| システム | 段階 | 判断 |
| --- | --- | --- |
| **ChatGPT** | Stage 2 | 長期記憶はあるが、システム全体のスケジューリングはない。 |
| **Claude** | Stage 2 | 作業記憶は強いが、自律的には発展しない。 |
| **Gemini** | Stage 1.5〜2 | 文脈とプロフィールが中心。 |

### 3.2 プロダクトの発展

主要な対話アプリの比較：

| アプリ | 特徴 |
| --- | --- |
| **ChatGPT** | **4 層のメモリ構成。**<br>**Saved Memory：** ユーザーが「Remember that…」と明示した内容を保存し、確認・削除できる。重要で明確、変わりにくい情報に向く。<br>**Session History：** 直近 1 日や数件のメッセージを保持する短期バッファ。順序を保ち、そのまま引用できる。<br>**Conversation Retrieval：** ベクトルデータベースから過去のメッセージを検索する。本調査では、正確な引用は過去 2 週間、それより古い内容は要約として扱うと説明している。検索単位は対話全体ではなくメッセージの塊で、各メッセージを埋め込み化して保存する。<br>**User Insights：** 「技術的な詳しい説明が好き」「Rust に詳しい」などの傾向を複数の対話から抽出する。同じ話題の履歴をまとめ、信頼度付きで要約する。<br>全体として、複雑な検索より大きな文脈と強いモデルによる統合に依存する。 |
| **Claude** | 明示的でプロジェクト単位のメモリ。CLAUDE.md などの編集可能なファイルに保存され、透明性、制御性、分離性が高い。自動推論より実装の信頼性や安全性を重視する。 |
| **Gemini** | 長期記憶と自動更新、ベクトル検索、要約圧縮、ユーザー特徴の集約。ユーザーの習慣を自動学習する方向に近い。 |
| **Qwen** | 明示的なきっかけ → 明確な書き込み。 |
| **豆包（Doubao）** | 暗黙の好みの抽出 → 自動的な発展。 |

ChatGPT のプロンプト構成の概略：

```
[システム指示と役割の説明]
[明示的な Saved Memory の一覧]
[User Insights の一覧]
--- retrieved context ---
[Conversation Retrieval の抜粋]
--- recent messages ---
[Session Buffer の直近 N 件]
User: <latest user message>
```

## 4 主要モジュール

4 層構成を参考にすると、一般的なエージェントのメモリは 4 種類のデータに分けられます。

### 4.1 データ

| 種類 | 定義 | 解決する問題・場面 | データ形式 | 使い方 |
| --- | --- | --- | --- | --- |
| **Saved Memory** | ニックネーム、年齢、性別など比較的変わりにくい基本情報や、保存・訪問・購入・評価した対象についての事実。 | 文脈の把握 | KV 保存 | 特定のクエリで能動的に呼び出す。 |
| **Current Session History** | 直近 30 分・1 時間・1 日の操作。開いた対象、検索クエリ、購入履歴、見た投稿など。 | 短期の文脈 | 実装側でリアルタイムに収集して連結 | 毎回の対話に受動的に組み込む。 |
| **Conversation Retrieval** | 過去の対話の要約。少数なら全部を使い、多数なら埋め込み化して検索する。 | 対話の継続性 | テキスト・埋め込み | 文脈に組み込む。 |
| **User Insights** | 行動や対話から推定した、個人属性、興味、長期的な好み、最近の意図。 | 個別対応と成長 | テキスト | 文脈に組み込む。 |

### 4.2 保存

| 種類 | 保存方法 |
| --- | --- |
| **Saved Memory** | KV 形式。オフラインのデータウェアハウスで T+1 更新し、オンライン KV へ取り込んで検索に使う。 |
| **Current Session History** | リアルタイムに収集し、端末・サーバー側で連結・解析する。機微性が高く量も多いため、データの扱いと圧縮を考慮する。 |
| **Conversation Retrieval** | セッション終了時に LLM で 1 文に要約し、直近 X 件を文脈へ入れる。 |
| **User Insights** | テキストのリストとして保存。各項目に信頼度、更新時刻、有効期間を付ける。以下に分類と JSON の例を示す。 |

**User Insights の分類テンプレート：**

| 分類 | ID | 内容 | 含める・除外する情報 | 特別な規則 |
| --- | --- | --- | --- | --- |
| **ニックネーム** | 0 | 呼ばれたい名前や呼び方 | 明示されたニックネームや呼称を含め、その他は除外する。 | 追加・更新のみ。削除は禁止。ニックネームのみ記録する。 |
| **基本情報** | 1 | ユーザーの識別情報 | 実名、ニックネーム、呼称を含め、連絡先、住所、職業、年齢などは除外する。 | — |
| **食の好み** | 2 | 食に関する好みと制約 | 味の傾向、アレルギー・宗教・健康上の制限を含め、食事の時刻・頻度、特定の店、一度限りの要望は除外する。 | — |
| **余暇の好み** | 3 | 能動的に表明された娯楽の好み | 余暇活動、旅行の好み、趣味・得意分野を含め、仕事の技能、受動的な参加、一度限りの体験は除外する。 | — |
| **家族関係** | 4 | ユーザーが言及した家族 | 配偶者、子、親、兄弟姉妹を含め、知らない人、サービス提供者、一度だけ会った人は除外する。 | — |
| **重要な日付** | 5 | 特別な意味を持つ日時 | 誕生日、記念日、大きな出来事、定期的な重要行事を含め、普通の約束、仕事の予定、一時的な計画は除外する。 | — |
| **対話の好み** | 6 | AI とのやり取りに関する希望 | 正式・気軽な文体、直接・婉曲な回答、長さ、口調を含め、本人の話し方、一時的な感情、その場限りの要望は除外する。 | — |

**保存用 JSON の例：**

```json
{
  "user_id": "u123",
  "time": "2025-04-20 19:00:00",
  "source": "dialogue",
  "key": "食の好み",
  "value": "辛い料理",
  "evidence": "胃がほぼ治ったので、また辛い料理を食べられる",
  "confidence": "high",
  "valid_time": "long"
}
```

### 4.3 更新

各セッション終了後に、LLM が 2 つの作業を行います。

| 作業 | 更新方法 |
| --- | --- |
| セッションの要約 | `{"tool": "add", "session_id": "...", "time": "...", "summary": "ユーザーが近くのおいしい和食を尋ね、エージェントが回答した..."}` |
| User Insights の更新判断 | `{"tool": "add"/"delete"/"edit", "key": "食の好み", "value": {"key": "食の好み", "value": "ユーザーは辛い料理が好き", "confidence": "high", "valid_time": "long"}}` |

### 4.4 検索

| 種類 | 検索方法 |
| --- | --- |
| **Saved Memory** | ツール呼び出しでキーを指定 → RAG で対象情報を検索 → テキストを返す。 |
| **Current Session History** | 実装側の API から直接取得し、時間窓に合わせて連結する。 |
| **Conversation Retrieval** | 平均ターン数が少なければ直近 N 件の要約を直接使い、量が多ければ埋め込み検索を使う。 |
| **User Insights** | 現在のクエリに関連する洞察を埋め込み検索で選び、文脈に入れる。 |

### 4.5 活用

| 方式 | モジュール | 内容 |
| --- | --- | --- |
| **能動的な呼び出し** | Saved Memory | エージェントがメモリツールを必要だと判断した場合のみ使う。 |
| **受動的な利用** | Current Session History | 毎回の対話の文脈に入れる。長さを管理する。 |
| **受動的な利用** | Conversation Retrieval | 同上。 |
| **受動的な利用** | User Insights | 同上。 |

## 5 その他の課題

**情報を利用・開示する範囲**

責任あるメモリシステムは、使ってよい情報と、話してよい情報を区別する必要があります。

- **利用も開示も可能：** 明示的な保存、閲覧、評価、はっきり表明された好み。
- **利用可能だが開示不可：** 行動から推測した予算傾向や購買力などの暗黙のラベル。
- **利用も開示も不可：** 宗教、政治的傾向、健康の詳細などの機微情報。
