## 概要

Claude Code の対話をまたぐメモリは、**ファイルシステムだけで実装された**永続化の仕組みです。ベクトルデータベースや埋め込みモデルは使わず、構造化した Markdown ファイルと LLM の理解に依存しています。中心となる考え方は、**コードベースそのものから推測できない情報だけを保存すること**です。

## 1. メモリの定義

### メモリとは

ユーザー、プロジェクト、協働の仕方についての**非構造化テキストの観察**を、対話をまたいで保持したものです。各メモリは独立した Markdown ファイルとして保存し、標準の frontmatter を付けます。

```
---
name: メモリの名前
description: 関連性の判断に使う、具体的な1行の説明
type: user | feedback | project | reference
---

メモリの本文
**Why:** このメモリを作った理由
**How to apply:** いつ適用するか
```

### 4 種類のメモリ

| 種類 | 保存する内容 | 典型的なきっかけ |
| --- | --- | --- |
| `user` | 役割、背景、技能、好み | データサイエンティストだと話す／Go は得意だが React は詳しくないと話す。 |
| `feedback` | Claude の行動への訂正や確認 | 「データベースをモックしないで」「この方法が良いので続けて」。 |
| `project` | 締め切り、判断の理由、進行中の仕事などの背景 | マージ凍結の開始日／あるモジュールを書き直す理由。 |
| `reference` | 外部システムへの参照 | バグは Linear の INGEST プロジェクトで管理している。 |

### 保存しない内容

次の内容は、明示的に頼まれてもメモリに**保存すべきではありません**。

- コードのパターン、構成、パス、プロジェクト構造：コードを読めばわかる。
- Git 履歴、最近の変更、誰が何を変えたか：`git log` と `git blame` が正しい情報源。
- デバッグ手順や修正方法：修正はコードにあり、背景はコミットメッセージにある。
- CLAUDE.md にすでに書かれている内容。
- 一時的なタスク状態や、現在の対話で進行している作業。

PR の一覧や活動のまとめを保存してほしいと言われたら、**意外だったことや自明でないことは何か**を尋ねます。それが保存する価値のある部分です。

## 2. 保存構造

### ディレクトリ構成

メモリは**プロジェクトごと**に分離され、現在の Git リポジトリのルートに基づいて配置されます。

```
~/.claude/projects/<sanitized-git-root>/memory/
├── MEMORY.md              ← 毎回読み込む索引
├── user_role.md           ← 個別のメモリ
├── feedback_testing.md
├── project_deadline.md
└── ...
```

`getAutoMemPath` のパス決定の優先順位：

1. Cowork 用の環境変数 `CLAUDE_COWORK_MEMORY_PATH_OVERRIDE`。
2. settings.json の `autoMemoryDirectory`。信頼するのは policy・local・user 由来の設定のみ。**プロジェクト内の .claude/settings.json は信頼しません**。悪意あるリポジトリが保存先を `~/.ssh` へ変えることを防ぎます。
3. 既定値：`~/.claude/projects/<sanitized-git-root>/memory/`。

同じリポジトリの worktree は、`findCanonicalGitRoot` によって同一のメモリディレクトリを共有します。

### MEMORY.md：索引

MEMORY.md は内容そのものではなく、**索引**です。1 件につき 1 行で記述します。

```
- [ユーザーの役割](user_role.md) — 可観測性に関心があるデータサイエンティスト
- [テストの規則](feedback_testing.md) — 過去の事故を理由にDBのモックを禁止
- [プロジェクトの期限](project_deadline.md) — マージ凍結 2026-03-05
```

厳格な制限があります。

- **最大 200 行：** 超えた部分は切り詰め、警告を付ける。
- **最大 25,000 バイト：** 長い行によるトークンの過剰消費を防ぐ。

索引は**毎回の対話でシステムプロンプトに直接挿入**されます。唯一、無条件で読み込まれるメモリです。

### メモリファイルの上限

走査する Markdown ファイルは最大 **200 件**。更新時刻の新しい順に選び、上限を超えたファイルはその対話では見えません。

## 3. メモリの生成：書き込み

書き込み経路は、**能動的な保存**と**バックグラウンド抽出**の 2 つです。

### 3.1 主モデルによる能動的な保存

対話中に Claude が保存の必要性を判断します。判断はシステムプロンプトの規則に従います。

**きっかけ：**

- 「そうしないで」「X をやめて」と行動を訂正される。
- 「そう、それでいい」と、自明でない方法を確認される。
- 「覚えておいて」と頼まれる。
- 役割、技能、好みなどの背景を知る。
- 締め切りや判断の理由など、プロジェクトの背景を知る。

**2 段階の保存手順：**

```
手順1：個別のメモリファイルを書く
  → Write ツールで feedback_testing.md を作る
  → frontmatter（name/description/type）と本文を入れる

手順2：MEMORY.md を更新する
  → ファイルへの参照を末尾に追加する
  → 形式：- [タイトル](filename.md) — 1行の要約
```

新しく作る前に、更新できる既存ファイルがないか調べ、重複を避けます。

### 3.2 バックグラウンド抽出：EXTRACT_MEMORIES

モデルがツール呼び出しをせず最終回答を出し、完全な query loop が終了すると、**メモリ抽出用のサブエージェント**が非同期で起動します。

```
ツール呼び出しなしで対話ターンが終了
    ↓
主モデルはこのターンでメモリを保存したか？
  ├── はい → 重複を避けてスキップ
  └── いいえ → 分岐したエージェントを起動
              ↓
         直近 N 件のメッセージを分析
              ↓
         保存する価値がある内容を判断
              ↓
         ファイルを保存し MEMORY.md を更新
```

権限は厳しく制限されます。

- 使用可能：Read、Grep、Glob、ls・find・cat・stat などの読み取り専用 Bash。
- 使用可能：Edit / Write。ただし**メモリディレクトリ内だけ**。
- 使用不可：MCP ツール、Agent ツール、書き込み可能な Bash、`rm`。

主対話と同じプロンプトキャッシュを使うため、追加のキャッシュは消費しません。

## 4. メモリの利用：読み込み

### 4.1 MEMORY.md は常に読む

対話の開始時に `loadMemoryPrompt()` が索引を同期的に読み、システムプロンプトの動的な部分へ挿入します。モデルは対話全体を通じて索引を参照できます。

### 4.2 関連ファイルを必要に応じて挿入する

各ターンの開始時、`startRelevantMemoryPrefetch()` は**主モデルのストリーミング回答と並行して**関連メモリを検索します。

```
ユーザーがメッセージを送る
    ↓
2つの処理を並行して開始：
  ① 主モデルを呼び、ストリーミング回答を生成
  ② 関連メモリを非同期で先読み：
       a. 各ファイルの name と description を読む
       b. ファイル名と説明の一覧を Sonnet に送る
       c. クエリに関連する最大5件を Sonnet が選ぶ
       d. 選ばれたファイルを全文読み込む
    ↓
主モデルの回答後、内容を次のターンへ添付する
```

`findRelevantMemories` の選択方法：

- キーワード照合やベクトル検索ではなく、**Sonnet による意味の選別**。
- 最近使ったツールの参考資料は、ノイズを避けるため推薦しない。
- 1 回に挿入するのは**最大 5 ファイル**。
- **セッション単位のバイト上限**で、文脈が膨らみすぎるのを防ぐ。
- `alreadySurfaced` で重複を除き、同じセッションで同じファイルを再挿入しない。

### 4.3 アクセスの規則

システムプロンプトには次の規則があります。

- 関連していそうなときは、能動的に読む。
- 「覚えて」「思い出して」と明示されたときは、**必ずメモリへアクセスする**。
- 「メモリを無視して」と言われたら、索引が空だと扱い、内容を適用・引用・言及しない。

## 5. 鮮度と検証

### 鮮度の表示

ファイルには更新時刻 `mtime` があります。古いメモリには、挿入時に次のような警告が付く場合があります。

```
このメモリは47日前のものです。記憶はある時点の観察であり、現在の状態ではありません。
コードの動作や file:line の参照は古くなっている可能性があります。
事実として述べる前に、現在のコードで確認してください。
```

今日または昨日に更新したメモリには、不要なノイズを避けるため警告を付けません。

### 使う前の検証

メモリに基づく提案の前に確認します。

- **ファイルパス**があれば、実際に存在するか調べる。
- **関数やフラグ**があれば、検索で確認する。
- ユーザーが行動しようとしているなら、先に検証する。

**「メモリに X があると書かれている」ことは、「今も X がある」こととは違います。**

記憶は保存時点のスナップショットです。現在のコードと矛盾するときは、**現在のコードを信頼し、古いメモリを更新・削除**します。

## 6. 更新と廃止

### 更新

新規作成の前に、既存ファイルを確認します。

```
1. MEMORY.md で関連項目を探す
2. 関連ファイルがあれば Edit で更新する
3. なければ新規作成し、索引に参照を追加する
```

name・description・type の frontmatter も、内容に合わせて更新します。

### 廃止

「忘れて」と頼まれたら、対象ファイルと索引の参照を削除します。

次の場合は能動的に更新・廃止します。

- 現在のコードや事実がメモリと矛盾する。
- 締め切りが過ぎた、決定が変わったなど、プロジェクトの状況が変化した。
- 参照先のパスや関数が存在しなくなった。

## 7. 似たメモリと矛盾するメモリ

### 自動の矛盾検出はない

Claude Code には**類似度計算や自動的な裁定の仕組みがありません**。似た内容や矛盾は、LLM の意味理解とプロンプトの規則に依存します。

### 書き込み時の重複防止

主モデル、バックグラウンド抽出、チームメモリの 3 つのプロンプトに、次の指示があります。

> 重複するメモリを書かないこと。新しく作る前に、更新できる既存のメモリがないか確認すること。

抽出エージェントにはさらに、名前・説明・更新時刻を含む**既存ファイルの manifest 一覧**が渡されます。

> 保存前にこの一覧を確認し、重複する新規ファイルを作るより既存ファイルを更新すること。

すでに何があるかは見えますが、似ているかどうかの判断はモデル自身が行います。ベクトル検索も類似度のしきい値もありません。

### 個人メモリとチームメモリの衝突

ここだけは**明確な矛盾処理の規則**があります。個人の `feedback` メモリについて、次のように定められています。

> 保存前にチームの feedback と矛盾しないか確認すること。矛盾する場合は保存しないか、上書きすることを明示すること。

個人の feedback でチームの規則を黙って上書きしてはいけません。保存をやめるか、どのチーム規則を上書きするかをファイルに記載します。

### 読み込み時の矛盾処理

自動で統合はせず、2 つの規則に従います。

1. **鮮度を優先：** 現在のコードと矛盾するときはコードを信頼し、メモリを更新・削除する（`MEMORY_DRIFT_CAVEAT`）。
2. **更新時刻を参考にする：** `mtime` の降順に並べ、manifest に ISO 時刻を含め、古い記憶に警告を付ける。

### 既知の限界

矛盾する 2 件がどちらも新しく、両方とも文脈へ選ばれた場合、**自動で矛盾を見つけて解決する仕組みはありません**。モデルは両方を読み、現在の対話に基づいて判断します。保存前の確認と使用時の検証で矛盾を減らしますが、完全な解消は保証しません。

## 8. ほかの永続化の仕組みとの違い

| 仕組み | 有効期間 | 用途 |
| --- | --- | --- |
| **メモリ** | 対話をまたいで永続 | ユーザーの好み、プロジェクトの背景、協働の仕方。 |
| **計画** | 現在の対話 | 実装方針の合意と計画。 |
| **タスク** | 現在の対話 | 進捗の管理と作業の分解。 |
| **CLAUDE.md** | コードベースに付随 | プロジェクトの規則とコードの慣習。Git で管理可能。 |

## 9. チームメモリ

機能フラグ `TEAMMEM` によって、2 つのディレクトリを使えます。

```
memory/           ← 個人メモリ：好み、仕事の進め方
memory/team/      ← チームメモリ：規則、テスト方針
```

種類ごとの既定スコープ：

| 種類 | 既定スコープ | 内容 |
| --- | --- | --- |
| `user` | 常に個人 | 個人情報は共有しない。 |
| `feedback` | 原則として個人 | 明確なプロジェクトの規則のみチームへ保存する。 |
| `project` | チームを強く推奨 | プロジェクトの状態は全員に役立つ。 |
| `reference` | 通常はチーム | 外部システムへの参照は共有する価値がある。 |

個人の feedback を保存する前にチームの feedback と照合し、上書きするなら関係を明示します。

## 10. 全体の流れ

```
新しい対話が開始
    │
    ├─ 同期：MEMORY.md を読む → システムプロンプトへ挿入
    │
ユーザーがメッセージを送る
    │
    ├─ 並行処理：
    │   ├─ 主モデルがストリーミングで回答
    │   └─ Sonnet が関連ファイルを非同期で選択
    │
    ├─ 関連ファイルの内容を添付する
    │
    ├─ 主モデルの回答中：
    │   └─ 能動的にメモリを保存するか判断
    │       ├─ はい → ファイルを保存し索引を更新
    │       └─ いいえ → 続行
    │
ツール呼び出しなしでターンが終了
    │
    └─ バックグラウンド：主モデルが保存したか確認
        ├─ 保存済み → スキップ
        └─ 未保存 → 抽出エージェントを起動
                    └─ 分析 → 判断 → 保存
```
