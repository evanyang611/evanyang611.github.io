## 1 背景

**"記憶（Memory）"是實現從"通用問答"向"私人助理"跨越的關鍵**。傳統檢索/問答系統主要基於關鍵詞匹配和短程上下文，是"無狀態"的，每次交互都是獨立的。而 AI Agent 的核心在於**"連續性"和"推理能力"**。目前痛點在於：

1. **Context Window 限制**：LLM 上下文窗口雖在變大，但將用戶幾年的歷史全部塞入 Prompt 既昂貴又會增加 Latency。
2. **個性化缺失**：通用大模型不知道用戶的口味偏好、專業背景、行為習慣。
3. **交互割裂**：用戶昨天問了"附近適合約會的餐廳"，今天問"我們要去哪？"，模型若無記憶則無法回答。

Agent 時代的核心機會在於：不僅利用對話數據（Chat），更能整合**行為數據（Action / Transaction）**。記憶模塊的目標是將這些異構數據轉化為 Agent 可理解的"認知"。


## 2 定義與目標


### 2.1 定義

AI Agent 的記憶模塊是一個**動態的讀寫系統**，它模仿人類大腦的工作方式，將海量原始數據壓縮、結構化存儲，並在需要時精準提取。它不僅僅是數據庫，更是**"存儲 + 檢索 + 反思"**的閉環。


### 2.2 核心目標

1. **個性化 (Personalization)**：基於歷史偏好（口味、場景、預算）進行精準推薦。
2. **連續性 (Continuity)**：支持多輪對話，記住上下文實體（Context Awareness）。
3. **成長性 (Evolution)**：隨著交互增多，Agent 對用戶的理解應越來越深（從"推熱門"變為"推你喜歡的"）。


### 2.3 需求場景

| 需求場景 | 描述 | 示例 |
| --- | --- | --- |
| **顯性需求** | 用戶直接提出個性化需求。查記憶 → 做決策 → 推薦 | • 根據我常去的川菜館推薦類似的店<br>• 總結我的口味偏好<br>• 基於我的偏好推薦 |
| **隱形需求** | 用戶未提及，但增加記憶信息後效果會更好。基於用戶畫像自動補全需求（口味、預算、常駐區域…） | 正例："望京附近好吃的"<br>負例：長沙本地人最推薦的火鍋 |
| **場景化能力** | 用戶短期狀態感知 | "最近感冒了" → 自動觸發清淡偏好 → 後續詢問康復情況 |
| **Session 記憶** | 短期上下文延續 | 剛瀏覽的店 / 筆記 → 下一步繼續推薦相關內容 |


### 2.4 評測標準與評測集

綜合多個開源評測集與相關論文，各主流 benchmark 普遍會使用到以下評估維度和指標：

| 評估維度 | 核心指標 | 常見度 | 評估方式 | 代表 Benchmark / 論文 | 判斷價值 |
| --- | --- | --- | --- | --- | --- |
| **記憶召回能力** | Accuracy / EM | ⭐⭐⭐⭐⭐ | 基於歷史提問，判斷是否命中正確記憶 | MemoryBank / MemoryAgentBench / MemBench | 所有體系的最低共識門檻 |
| | Recall@K | ⭐⭐⭐⭐⭐ | 看 memory / retrieval 是否命中關鍵證據 | LoCoMo / MemBench | 比 Accuracy 更能反映 memory 結構好壞 |
| **回答是否基於真實記憶** | Response Correctness | ⭐⭐⭐⭐ | 回答是否依賴真實歷史而非編造 | MemoryBank | 防"看起來像對，其實是編的" |
| **長期一致性** | Contextual Coherence | ⭐⭐⭐⭐ | 多輪對話中語氣、人設、狀態是否連貫 | MemoryBank / LoCoMo | 偏主觀，但非常產品向 |
| **時間 / 因果理解** | Temporal / Multi-hop QA | ⭐⭐⭐⭐⭐ | 跨時間、多事件推理是否正確 | LoCoMo / EventQA | 長期記憶 vs 長上下文的分水嶺 |
| **事件建模能力** | Event Summarization (FactScore) | ⭐⭐⭐⭐ | 是否正確還原事件時間線 | LoCoMo | 不看文采，只看事實 |
| **記憶更新能力** | Selective Forgetting Accuracy | ⭐⭐⭐⭐ | 新事實是否覆蓋舊事實 | MemoryAgentBench / MemBench | 目前全行業最容易翻車的點 |
| **在線學習能力** | Test-Time Learning Accuracy | ⭐⭐⭐⭐ | 能否從歷史示例中學會新規則 | MemoryAgentBench / Evo-Memory | Agent 時代的關鍵能力 |
| **反思 / 抽象能力** | Reflective Memory Accuracy | ⭐⭐⭐⭐ | 是否能從多事實中總結偏好 / 畫像 | MemBench | 對齊 persona / user insight |
| **規模魯棒性** | Memory Capacity Curve | ⭐⭐⭐ | 噪聲增大時性能是否斷崖下跌 | MemBench | 非常工程 & 生產向 |
| **系統效率** | Read / Write Latency | ⭐⭐⭐ | 記 / 取 memory 的時間成本 | MemBench | 決定能不能上生產 |


## 3 行業調研

跨模型、跨產品的一致共識是：**Memory = 支撐"長期個性化 + 任務連續性"的核心基礎設施**。它普遍由三個動作組成：

1. **寫入（Write）**：從對話、行為、任務中抽取可複用信息（偏好、約束、事件、知識等）。
2. **管理（Process）**：對記憶進行合併、抽象、去重、遺忘、衝突處理、結構化組織。
3. **讀取（Read）**：在需要時檢索並注入模型，輔助 query rewrite、推理決策與結果過濾。

Memory 的目標從"延長上下文"演進為：

- 建立用戶畫像（Who）
- 保留時間線行為（When / What）
- 支撐任務級推理（Now / Next）


### 3.1 學術領域的發展

學術界對 Memory 的探索大致可以劃分為三個演進階段：

| 階段 | 階段名稱 | 核心 Memory 形態 | 關鍵技術特徵 | 能解決什麼問題 | 主要侷限 | 代表工作 / 系統 |
| --- | --- | --- | --- | --- | --- | --- |
| **Stage 1** | 短期 / Trial 內 Memory | 對話歷史、軌跡、summary | history 拼接、摘要壓縮 | 多步推理、任務內連貫 | 任務結束即清空 | Generative Agents（早期）、MemGPT（早期） |
| **Stage 2** | 外掛式長期 Memory<br>（Memory as Component） | 外部存儲（向量 / KV / Graph） | 抽取 → 存儲 → 檢索；支持跨 session | 跨對話記憶、偏好複用 | 碎片化、弱一致性、persona 非內建 | Mem0、A-Mem、Zep、MemoryBank |
| **Stage 3** | 系統級 Memory<br>（Memory as Operating System） | 分層長期記憶 | STM / MTM / LTM；事件流；自動更新與遺忘 | 長期一致人格、跨任務演化 | 工程複雜、仍在探索 | MemoryOS、EverMemOS、MIRIX |

主流 APP 處於什麼階段的判斷維度：

| 判定維度 | Stage 2（組件） | Stage 3（系統） |
| --- | --- | --- |
| **是否自動寫入** | 需要顯式觸發（如"記住這個"） | 模型 / 系統自動抽取 |
| **是否可更新 / 覆蓋** | 基本不支持 | 支持衝突解決、修正 |
| **是否有時間線** | 無 / 弱 | 明確事件流 |
| **是否影響行為策略** | 主要影響回覆 | 影響規劃、工具選擇 |

據此對主流系統的定位判斷：

| 系統 | 當前階段 | 核心判斷 |
| --- | --- | --- |
| **ChatGPT** | Stage 2 | 有長期記憶，但無系統級調度 |
| **Claude** | Stage 2 | 強工作記憶，但不自主演化 |
| **Gemini** | Stage 1.5 ~ 2 | 以 context 和畫像為主 |


### 3.2 行業領域的發展

主流對話 APP 的記憶機制對比：

| APP | 特點 |
| --- | --- |
| **ChatGPT** | **四層記憶架構**<br>• **Saved Memory（顯式記憶）**：用戶明確說"Remember that…"才會寫入，可查看、可刪除。適用於關鍵、明確、不易變化的用戶信息。<br>• **Session History（短期 buffer）**：只存最近一天 / 幾條消息。完整、順序、可被逐字引用。<br>• **Conversation Retrieval（跨會話 RAG）**：靠向量數據庫檢索舊消息，只能精確引用 2 周內的內容，更舊的只能給摘要。檢索粒度是"消息塊"，非完整會話流。每條消息經 embedding 寫入向量數據庫。<br>• **User Insights（隱式洞察）**：系統自動從多次對話中總結規律，例如"你喜歡技術細節"、"你寫 Rust 很熟"。對同主題歷史消息聚類，再總結，附帶置信度。<br>整體上更依賴"大上下文 + 強模型整合"，而非複雜檢索。 |
| **Claude** | • **完全顯式、項目級記憶**<br>• 記憶保存在可編輯文件中（如 CLAUDE.md）<br>• **透明可控、隔離性強**<br>• 強調工程可靠性與安全性，而非自動推斷 |
| **Gemini** | • 長期記憶 + 自動更新<br>• 向量檢索、摘要壓縮、用戶特徵聚合<br>• 更接近"自動學習用戶習慣"的路線 |
| **Qwen** | • 顯式觸發 → 明確寫入 |
| **豆包** | • 隱式偏好抽取 → 自動演進 |

ChatGPT 的 Prompt 大致組織形式：

```
[系統指令 + 角色說明]
[顯式 Saved Memory 列表]
[洞察 Insights 列表]
--- retrieved context ---
[Conversation Retrieval 片段]
--- recent messages ---
[Session Buffer 最近 N 條]
User: <latest user message>
```


## 4 關鍵模塊

參考 ChatGPT 的四層記憶架構，可以把一個通用 Agent 的記憶模塊拆解為四種數據形態：


### 4.1 數據

| 記憶類型 | 定義 | 解決的問題 / 場景 | 數據形式 | 使用方式 |
| --- | --- | --- | --- | --- |
| **Saved Memory**<br>顯式記憶 | 事實類數據，包括用戶幾乎不會更改的基本信息（暱稱、年齡、性別等），以及用戶歷史收藏 / 打卡 / 消費 / 評論過的實體 | 上下文感知 | KV 形式存儲 | 特定 query 主動調用 |
| **Current Session History**<br>實時行為 | 近實時交互行為，用戶近 30min / 1h / 1d 內的操作：點開的實體 / 搜索 query / 消費記錄 / 瀏覽筆記等 | 短期上下文 | 工程側實時提取 + 拼接 | 每次對話被動拼入 |
| **Conversation Retrieval**<br>對話檢索 | 歷史對話的總結摘要，對最近每一條對話做 summary，如果數量不多則全量使用，數量多則 embedding 後 RAG | 對話連續性 | Text / Embedding | 拼接到上下文中 |
| **User Insights**<br>用戶洞察 | 對用戶的猜想。從歷史行為與對話中提取出的個人屬性、興趣標籤、長期偏好、最近意圖 | 個性化、成長性 | Text 形式存儲 | 拼接到上下文中 |


### 4.2 存儲

| 記憶類型 | 存儲形式 |
| --- | --- |
| **Saved Memory**<br>顯式記憶 | KV 格式存儲，離線數倉 T+1 更新，導入線上 KV 存儲供檢索取用 |
| **Current Session History**<br>實時行為 | 工程側實時採集 + 端上 / 服務端拼接解析。數據敏感、量大，通常需要考慮合規與壓縮策略 |
| **Conversation Retrieval**<br>對話檢索 | 每個 session 結束後，使用 LLM 概括成一句話總結。每次選取最近 X 條總結，拼入上下文 |
| **User Insights**<br>用戶洞察 | 採用 List of Text 存儲，每條附帶 **置信度、更新時間、有效時間**。參考如下 persona 分類模板與 JSON 結構 |

**User Insights 分類模板：**

| 分類名稱 | ID | 描述 | 核心篩選標準（包含 / 排除） | 特殊規則 |
| --- | --- | --- | --- | --- |
| **用戶暱稱** | 0 | 用戶暱稱或稱呼偏好 | 包含：用戶明確提供的暱稱、希望被稱呼的名字<br>排除：非暱稱類信息 | 僅允許「更新 / 新增」，禁止刪除；只記錄暱稱 |
| **用戶基礎信息** | 1 | 用戶身份標識信息 | 包含：真實姓名、暱稱、稱呼偏好<br>排除：聯繫方式、地址、職業、年齡等敏感信息 | - |
| **飲食偏好** | 2 | 食物消費相關偏好 / 限制 | 包含：口味傾向、忌口（過敏 / 宗教 / 健康）<br>排除：用餐時間 / 頻次、特定餐廳偏好、一次性需求 | - |
| **休閒娛樂偏好** | 3 | 用戶主動表達的娛樂偏好 | 包含：休閒活動、旅行偏好、愛好特長<br>排除：工作技能、被動參與、一次性體驗 | - |
| **家庭關係** | 4 | 用戶提及的家庭關係 | 包含：配偶、子女、父母、兄弟姐妹<br>排除：陌生人、服務提供者、一次性接觸人員 | - |
| **重要時間節點** | 5 | 用戶特殊紀念意義時間 | 包含：生日 / 紀念日、重大事件時間、定期重要活動<br>排除：普通約會、工作日程、臨時安排 | - |
| **溝通偏好** | 6 | AI 交互方式的偏好要求 | 包含：回覆風格（正式 / 隨意）、回答方式（直接 / 委婉）、長度語氣<br>排除：用戶自身表達習慣、臨時情緒化要求、單次場景需求 | - |

**存儲 JSON 結構示例：**

```json
{
  "user_id": "u123",
  "time": "2025-04-20 19:00:00",
  "source": "dialogue",
  "key": "飲食偏好",
  "value": "辣",
  "evidence": "胃好得差不多了，又可以吃辣了",
  "confidence": "high",
  "valid_time": "long"
}
```


### 4.3 更新

每次 session 完成後，使用 LLM 完成兩項工作：

| 任務 | 更新方式 |
| --- | --- |
| 概括本 session 內容 | `{"tool": "add", "session_id": "...", "time": "...", "summary": "用戶提問了附近好吃的日料，Agent 回答了..."}` |
| 判斷是否要更新 User Insights | `{"tool": "add"/"delete"/"edit", "key": "飲食偏好", "value": {"key": "飲食偏好", "value": "用戶喜歡吃辣", "confidence": "high", "valid_time": "long"}}` |


### 4.4 檢索

| 記憶類型 | 檢索方法 |
| --- | --- |
| **Saved Memory**<br>顯式記憶 | tool call 指定特定 key → RAG 檢索實體信息 → 返回文本信息 |
| **Current Session History**<br>實時行為 | 直接由工程側接口拉取，按窗口拼接 |
| **Conversation Retrieval**<br>對話檢索 | 若平均對話輪次較少，可直接把最近 N 條 summary 拼入上下文；量大時啟用 embedding 檢索 |
| **User Insights**<br>用戶洞察 | 通過 embedding，根據當前 query 提取最相關的洞察，注入上下文 |


### 4.5 利用

| 利用方式 | 對應模塊 | 說明 |
| --- | --- | --- |
| **主動調用** | Saved Memory 顯式記憶 | 只有當 Agent 判斷需要調用 memory 工具時才使用 |
| **被動使用** | Current Session History 實時行為 | 拼入上下文使用，每次對話都可用（注意控制上下文長度） |
| **被動使用** | Conversation Retrieval 對話檢索 | 同上 |
| **被動使用** | User Insights 用戶洞察 | 同上 |


## 5 其他問題

**信息使用邊界**

一個負責任的 Agent 記憶系統需要明確劃定信息的可用性與可透露性：

- **能用能說**：顯式收藏、瀏覽、評價、明確表達的偏好
- **能用不能說**：行為推斷的隱性標籤（如預算傾向、消費能力）
- **不能用也不能說**：敏感類信息（宗教、政治傾向、健康詳情等）
